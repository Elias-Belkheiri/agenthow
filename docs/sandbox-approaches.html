The execution boundary

Where should the code run?

Eight ways to handle model-generated Python—from not running it at all to giving it a separate machine. The key question is not whether code runs in another process, but what it can do if the restrictions fail.

This is a design guide, not a security certification. Agent Smith has a fake-tested loop; its real sandbox and providers are not implemented.

Threat model

Assume the code wants out.

Generated Python might be buggy, infinite, or actively hostile. It can try to import forbidden modules, follow a symlink to a secret, open a socket, fork a process, exhaust memory, or introspect Python objects to recover powerful capabilities. A test that blocks import os does not prove that every route to the operating system is closed.

The PDF's requirement

Configured import and directory allowlists, no network, restricted builtins, hard code timeout and memory limits. Its security mechanisms must use standard Python libraries and builtins; it does not mandate one isolation topology. Whether an external container runtime is permissible and installed in evaluation must be confirmed.

Approach index
01 / ZERO EXECUTION

Parse, inspect, and stop.

Accept a fenced Python action and check its structure, but never call an executor. There is no runtime to escape because the code never runs.

Strength

A reliable development gate while writing extraction, accounting and control flow. No external runtime dependency.

Limit

Cannot run MBPP tests, inspect dynamic behavior or produce actual sandbox observations. Syntax checks do not prove a solution works.

Agent Smith now: fake executors return fixed observations; this is the only mode currently proven by loop tests.
02 / SAME PROCESS

Restrict names and syntax.

Run Python in the agent process with a small globals dictionary, selected builtins, AST checks and import wrappers.

Strength

Fast and easy to prototype. Useful as an additional policy layer or for cooperative code.

Limit

Code shares the agent's memory and privileges. Introspection, native modules or implementation mistakes can recover capabilities; an infinite loop can seize the agent. Not a hostile-code boundary.

Agent Smith fit: policy checks may supplement isolation, never replace it.
03 / SEPARATE PROCESS

Give Python its own worker.

Start a child interpreter with restricted builtins and imports. Send actions through a narrow channel; set resource limits where available and kill the worker on timeout.

Strength

Agent survives most worker crashes; execution state and timeouts are easier to control. Standard-library implementation can match the local CLI.

Limit

Normally inherits the host user's file and network privileges. Python-level hooks and allowlists can be bypassed by hostile code; platform resource limits vary. A subprocess alone is not strong isolation.

Agent Smith fit: chosen as the minimum architecture's process boundary, explicitly best-effort until backed by OS controls and tests.
04 / KERNEL POLICY

Let the OS enforce denial.

Put the worker under OS-level filesystem, network, process and resource restrictions. On Linux these may involve namespaces, Landlock, seccomp and cgroups; mechanisms and privilege requirements differ on macOS and Windows.

Strength

Restrictions survive many Python-level bypasses because the kernel rejects prohibited operations.

Limit

Complex, platform-dependent setup. One primitive does not cover everything: for example, resource limits do not deny network, and path checks do not isolate processes. Must fail closed if unavailable.

Agent Smith fit: best direction for hostile code if the actual evaluator OS exposes usable mechanisms.
05 / CONTAINER

Package the OS boundary.

Run each task in a hardened container with no network, only explicitly mounted workspaces, a read-only root, dropped capabilities, process limits, and CPU/RAM quotas.

Strength

A practical way to combine several kernel controls and reset state per run. Clear path to a narrow workspace and disposable scratch area.

Limit

Requires an available runtime and correct image/mount/daemon configuration. Containers share a host kernel and are not automatically secure; a mounted Docker socket is especially dangerous.

Agent Smith fit: attractive if Docker/Podman is allowed and present in the grading environment; this is not established yet.
06 / SEPARATE KERNEL

Use a VM or microVM.

Start the worker inside a guest with its own kernel; exchange input and results over a narrow host–guest channel.

Strength

Stronger separation from the host than a shared-kernel container and a clean disposable environment.

Limit

Provisioning, images, startup time and memory overhead are substantial for a 120-second MBPP task. MicroVM availability is platform-specific.

Agent Smith fit: defensible for a production hostile-code service, likely disproportionate for this local first milestone.
07 / SEPARATE HOST

Send execution to a remote runner.

A dedicated machine or managed code-execution service receives actions and returns bounded observations.

Strength

Separates the developer host from execution, centralizes isolation and can scale many jobs.

Limit

Introduces deployment, credentials, latency, network availability and data-transfer concerns. The remote runner still needs a sandbox internally.

Agent Smith fit: poor match for a self-contained local evaluator unless a runner is supplied.
08 / CAPABILITY RUNTIME

Run Python atop WASM/WASI.

Use a Python runtime compiled to WebAssembly and expose only explicit filesystem, clock or network capabilities.

Strength

Capability-based design with an execution engine distinct from native CPython; potentially strong containment for supported workloads.

Limit

Python 3.10 behavior, native packages, process APIs, memory limits and later MCP integration may diverge. The runtime itself is an extra dependency.

Agent Smith fit: a research alternative, not a drop-in answer to the evaluator's Python environment.
Regardless of topology

What must be tested before the first real action?

01 / Imports + builtins

Only configured modules; dangerous entry points denied; test indirect access, not just simple imports.

02 / Files + symlinks

Allowed directories as seen inside the worker; outside paths and escaping symlinks denied, including writes.

03 / Network + processes

Outbound and inbound connections blocked. No unrestricted child processes or host-control sockets.

04 / Time + RAM

Terminate runaway code and excessive allocation, with parent recovery and descendant cleanup.

05 / Output + errors

Bound stdout/stderr and observations; report partial output on timeout. Propagate SystemExit and KeyboardInterrupt correctly.

06 / Trusted bridge

Keep final_answer in the sandbox namespace. Later MCP tools use a trusted broker, not direct generated-code network access.

The unresolved architecture choice

Where to draw the first real boundary

These are implementation choices, not two equivalent security guarantees.

Option A · original minimum plan

Restricted subprocess

Build the standard-library child worker, resource limits and policy checks first; keep its limitation explicit.

  • Smallest dependency footprint.
  • Can validate loop/worker communication.
  • Cannot honestly promise hostile-code isolation from Python filtering alone.
Option B · stronger gate

OS or container enforcement

Require kernel-enforced filesystem and network denial around the restricted worker before live model output runs.

  • More defensible security boundary.
  • Needs verified evaluator OS, privileges and runtime availability.
  • Should fail closed if required enforcement is absent.
Recommended direction

Combine the narrow Python worker interface with OS-enforced isolation. Confirm exam runtime and PDF policy first; specify the exact mechanism and write escape tests. Until those pass, keep the fake executor. No decision or implementation is being claimed by this page.
