Architecture field guide / Linux-first

OS-level sandboxing
vs containerization

Two ways to constrain a process—but not two separate security technologies. A container usually assembles OS isolation primitives around a packaged application; a sandbox is the enforcement boundary and policy you choose.

01 / Define the boundary

Isolation is a spectrum, not a product name.

OS-level sandboxing applies kernel-enforced restrictions to a process or process tree: which files it can see or access, which system calls it may make, which identities it holds, whether it can use the network, and how many resources it can consume. A policy may be assembled directly around a single worker without a container image.

Containerization adds an operational unit: an image/root filesystem, runtime, lifecycle, distribution and repeatable deployment. On Linux, the runtime normally uses many of the same kernel mechanisms to isolate the container’s processes. An image is packaging, not a security boundary.

Key distinction: “sandbox vs container” is not a mutually exclusive choice. A container can be a sandbox if configured and enforced as one; a sandbox can be implemented without a container. Neither term alone guarantees safe execution of hostile code.

02 / Layered architecture

Where the boundaries actually sit

What each primitive does: mount/PID/network/IPC/user namespaces change what a process can see or which identity it has; cgroups bound CPU, memory and process counts; seccomp filters system calls; LSMs constrain permitted operations on objects. None is a complete sandbox alone. For example, a network namespace needs no usable interface (or an equivalent enforced policy) to deny networking; a read-only root does not make writable host mounts safe.

Platform note: these are Linux mechanisms. macOS and Windows use different controls; Docker Desktop typically runs Linux containers inside a Linux VM, so its kernel boundary relative to the desktop host differs from native Linux containers.

03 / Control & data flow

One untrusted task, end to end

Direct sandbox startup

  1. Create a disposable workspace and narrow input/output channel.
  2. Enter namespaces and/or apply filesystem, privilege and syscall restrictions in the safe order required by the platform.
  3. Set resource limits, start the worker, supervise the process tree and remove temporary state.

Container startup

  1. Select a pinned image and explicit runtime policy; avoid privileged mode and host-control sockets.
  2. Runtime prepares rootfs, namespaces, mounts, cgroups and security profiles, then launches the process.
  3. Controller enforces deadline/output limits; runtime stops the container and disposes of writable state.

Failure rule: if a required restriction cannot be applied, reject the job rather than silently running it with weaker permissions. A timeout without process-tree cleanup, or a path allowlist that can be bypassed with symlinks or mounted directories, is not containment.

Direct sandbox: strengths / costs

Small deployment surface and fine-grained, auditable policy for a narrow worker. The price is platform-specific engineering, tricky setup order and responsibility for lifecycle, filesystem layout and cleanup.

Containers: strengths / costs

Repeatable user space and a familiar deployment interface, especially useful for many dependencies or teams. The price is image/runtime operations and dangerous configuration shortcuts; an unhardened container is not a hostile-code boundary.

05 / Choosing a design

Choose by threat model, not terminology.

  • Known, cooperative code on one controlled host: a direct process sandbox may be simpler and faster to operate if the required OS policies are available.
  • Repeatable app deployment with managed dependencies: use containers, then explicitly harden identities, mounts, networking, capabilities, syscall policy and resource limits.
  • Untrusted tenant or model-generated code: treat either shared-kernel design as exposure to kernel attack surface. Use defense in depth (restricted API + OS policy + disposable workspace + strict supervision); consider a VM/microVM or remote isolated host when the consequence of escape warrants a separate kernel boundary.

Practical default for untrusted code: put a minimal worker inside a hardened, disposable container if a verified runtime is available; otherwise use an equivalently enforced direct OS sandbox. Deny host-control sockets, minimize mounts, run without root/extra capabilities, block network unless explicitly needed, cap CPU/RAM/processes/output/time, and test attempted escape paths. If the host cannot enforce the required policy, do not run the task.

Review questions: What is the attacker allowed to submit? Which kernel is shared? Which host paths and descriptors are exposed? Who can change runtime policy? What happens when a control fails? Can one task affect another? How do you test denial and cleanup?

Reference concepts: Linux namespaces, cgroups, seccomp and LSMs; OCI image/runtime specifications. This is an architecture explainer, not a security certification or a claim that any particular configuration has been tested.
